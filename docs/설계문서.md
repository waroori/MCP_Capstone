## 0. 용어

이 문서와 화면·발표는 아래 말을 쓴다. 코드의 enum·API 이름은 영어 그대로 두고, 화면 라벨(`apps/admin_web/src/labels.js`)에서만 바꾼다.

| 사용자 말 (화면·발표·이 문서) | 뜻 | 코드 |
| --- | --- | --- |
| 제품, 구독 | 회사가 계약해 직원에게 할당한 AI·소프트웨어 서비스 (ChatGPT Enterprise, Claude API, Canva Enterprise 등) | `tools`, `contracts` |
| 승인 제품 | 사내 사용이 허용된 제품 | `approval_status=approved` |
| 이용권 | 제품의 좌석 1개 | `seat_assignments` |
| 처리 요청 | 데이터를 바꾸는 일의 요청서. 승인 뒤 또는 즉시 처리됨 | `action_plans` (plan) |
| 승인 대기 | 관리자가 결정해야 하는 처리 요청 목록 | `status=pending_approval` |
| 바로 처리 / 담당자 승인 / 책임자 결정 | 처리 요청의 세 단계 | `risk_level` low / medium / high |
| 토큰 사용 경보 | 좌석 토큰 소비 속도가 평균의 2배를 넘은 알림 | `anomalies` (rule `seat_pace_2x`) |
| 미지원 요청 | 승인 제품으로 할 수 없었던 직원 요청의 기록 | `unmet_needs` |
| 참고한 데이터 | 에이전트가 답을 만들 때 읽은 기록 | `evidence` |
| 아낀 구매 비용 / 줄어든 청구 / 예상 절감 | 절감 종류 | `savings_ledger.kind` |
| AI 비서 | 직원·관리자가 대화하는 에이전트 | agent_runtime |
| MCP 도구 (엔지니어링 전용) | 에이전트가 부르는 조회·변경 함수. 업무 자체를 수행하지 않고 우리 관리 데이터만 읽고 쓴다 | `schemas.mcp_tools` |

**에이전트가 하지 않는 일.** 직원의 업무(문서 비교, 분류, 요약)는 직원이 자기에게 할당된 제품에 시킨다. 우리 에이전트는 "어떤 제품·모델을 쓰면 되는가", "이 기능을 회사 플랜에서 써도 되는가", "이용권을 달라"처럼 **제품 선택과 사용 권한, 운영**에 관한 요청만 다룬다.

## 1. 개요와 범위

회사가 구독하는 AI와 소프트웨어를 직원이 업무에 맞게 쓰도록 돕고(활용 지원), 구독 자산과 비용을 한 사람이 관리할 수 있게 한다(운영 지원). AI가 끼어드는 곳은 에이전트 런타임 한 곳이고, 나머지는 코드와 MCP가 한다.

### 타깃
| 구분 | 대상 | 전제 |
| --- | --- | --- |
| 주 타깃 | AX 전환 중인 비IT 중견기업 (구독 이용자 수십~수백 명) | 사용량 기반 엔터프라이즈 AI 플랜과 좌석제 SW 구독을 함께 쓰고, 관리 인원은 한두 명 |
| 도입 단계 타깃 | 비즈니스 구독에서 엔터프라이즈로 넘어가는 소기업 | 관리 API가 제한적이라 이용권·업무를 수동 등록 |

### 범위 (v2)
| 기능 | MVP | 후속 |
| --- | --- | --- |
| F1 업데이트 기반 활용 제안 | 주 1회 수집 → 시스템 계정 에이전트가 관련 팀 판단 → 알림 정책 통과 시 팀 Slack 자동 발송 → 판단 기록 화면 | 판단 기록 메일 발송, 교육 과정 편성 |
| F2 업무별 제품·모델 추천 | Slack 질의 → 조건 확인 → 평가 결과 기반 추천, 예상 비용, 테스트 환경 변경 요청. AI가 필요 없으면 일반 제품으로 안내 | 샘플 비교 평가 실행기 |
| F3 사용량·비용 알림 | 10~30분 수집 → 임계치 → 알림. 관리자가 원인 조사 요청(또는 자동 조사) | 실시간 스트리밍, 예측 |
| F4 이용권 현황·배정 | 신청 → 좌석 있으면 즉시 배정, 없으면 AI 의견 + 승인 대기 → 회수·재배정 1건 | 갱신 수량 리포트, SSO·SCIM |
| F5 미지원 요청 | F2에서 승인 제품으로 안 되는 요청을 기록·집계해 관리자에게 표시 | 후보 제품 비교 |
| 비AI 구독 (v2) | Adobe 1개 벤더를 Mock으로 추가. 이용권·비용 흐름을 같은 구조로 시연 | Microsoft 365 등 |

실제 벤더 연동은 하지 않는다. 모든 벤더 데이터는 실제 관리 API 구조를 본뜬 Mock 서버다.

### 설계 원칙
1. 계산은 코드, 해석과 판단은 에이전트, 연결과 권한 경계는 MCP가 맡는다.
2. 대화 내용을 수집하지 않는다. 사용 메타데이터, 직원이 등록한 업무, AI 비서에 요청한 내용만 쓴다.
3. 활용 데이터는 교육·제품 개선에만 쓰고 인사평가에 쓰지 않는다. 팀 단위(5명 이상)로만 본다.
4. 데이터를 바꾸는 일은 처리 요청(plan)으로만 하고, 실행은 승인된 plan_id로만 한다. 실행 직전에 서버가 상태를 다시 확인한다.
5. 사용 기록이 없으면 미사용이 아니라 확인 필요다. 무응답은 회수 사유가 아니다.
6. 외부 정보는 허용 목록 벤더의 공식 문서만 쓴다.
7. 승인은 단계를 둔다. 되돌릴 수 있는 일은 바로 처리하고 기록만 남긴다. 느린 승인은 섀도 AI의 원인이다.
8. **(v2)** 에이전트는 상시 실행하지 않는다. 사람 요청 또는 배치 조건 충족 시에만 한 번 실행되고 끝까지 간다.

## 4. 시나리오 (v2)

[ ]는 주체, **굵게**는 사람이 결정하는 지점.

### A — 업데이트를 팀에 자동 제안 (F1)
1. [배치·주 1회] 허용 목록 벤더의 릴리스 노트를 수집해 새 항목을 저장한다. 새 항목이 있으면 시스템 계정으로 에이전트를 한 번 호출한다.
2. [에이전트] `get_vendor_update`, `list_approved_tools`로 회사 플랜에 있는 기능인지 본다. 없으면 `save_suggestion(status=on_hold, hold_reason)`으로 사유를 남기고 끝낸다.
3. [에이전트] `find_relevant_tasks`로 직무·등록 업무 후보를 받아 관련성을 판단한다. 근거가 있는 팀에만 제안을 쓰고 저장한다. 근거가 없으면 보류 사유를 남긴다.
4. [백엔드] 알림 정책(9절)을 코드로 검사한다: 주 2건 상한, 평일 09~18시, 근거 필수, "관련 없음" 2회면 4주 보류, 팀별 발송 스위치.
5. [백엔드] 통과한 제안을 팀 Slack 채널로 보낸다. 사람 승인 없음.
6. [직원] 도움 됨 / 관련 없음 / 적용 방법 질문으로 반응한다. 질문은 F2 대화로 이어진다.
7. [관리자] "자동 제안 기록" 화면에서 업데이트별로 어느 팀에 뭘 보냈고 왜 안 보냈는지 본다. (후속: 같은 내용을 HRD에 메일)

### B — 업무 설명으로 제품·모델 추천 (F2)
1. [직원] Slack에 업무를 설명한다. "고객 문의 1,000건을 매일 10개 유형으로 분류하는데 비용을 줄일 수 있나요?"
2. [에이전트·의도 분류] 제품·모델 추천으로 분류한다.
3. [에이전트·조건 확인] 하루 건수, 입력 길이, 정확도 기준, 응답 시간, 채팅 좌석인지 API인지가 부족하면 한 번에 묻고 끝낸다. 답이 오면 같은 대화에서 이어간다.
4. [에이전트] AI가 필요 없는 요청(예: PDF 편집)이면 승인된 일반 제품을 안내하고 이용권 신청으로 넘긴다.
5. [에이전트] API 업무면 `list_approved_models`, `get_usage_summary`, `get_eval_results`를 본다. 평가 결과가 없으면 추천하지 않고 "평가 필요"라고 답한다(MVP는 답변까지).
6. [에이전트] 품질 기준 통과 후보만 남기고 `estimate_task_cost`로 월 비용을 비교해 추천·이유·비용·확인 사항을 답한다.
7. 변경을 원하면 `create_action_plan(model_change, test)`을 만든다. **관리자가 승인하면** 실행된다.
8. 승인 제품 어느 것도 못 하는 요청이면 `record_unmet_need`로 미지원 요청을 남기고 그 사실을 알린다.

### C — 좌석별 토큰 소비 속도 경보 (F3)
1. [배치·5분] 토큰을 세는 좌석(`contracts.daily_token_quota > 0`, 지금은 ChatGPT Enterprise)의 직원별 사용량을 수집한다. 지금은 더미 수집기(`collect_usage`)이고, 실제 연동 때는 이 함수만 벤더 사용량 API로 바꾼다.
2. [배치] 소비 속도 = 오늘 예상량(지금까지 사용량 ÷ 근무 9–18시 중 지난 비율) ÷ 같은 제품 좌석의 최근 14일 평균 하루 사용량. 1.5배 이상이면 '빠름', **2배 이상이면 경보**(`seat_pace_2x`). 하루에 이미 평균의 25%는 써야 경보한다(아침 오탐 방지). 같은 사람은 하루 한 번만.
3. [Slack] 본인에게만 DM: "토큰 사용량이 많은 작업 중이에요! 모델 변경을 권해 드려요…" + **[현재 작업 분석]** 버튼.
4. [에이전트] 버튼을 누르면 본인 권한으로 `analyze_seat_usage`: `get_seat_usage`(시간대·입력 길이·모델 분포)로 이유를 짧게 추정하고(단정하지 않음) 같은 좌석의 더 가벼운 승인 모델을 하나 권한다.
5. [관리자] 좌석 배치도에서 자리 색(빠름·2배 이상)과 마우스 호버로 오늘 사용량·예상량·한도 %를 보고, 자리를 누르면 분포와 [AI로 현재 작업 분석]이 나온다. 홈 '지금 확인할 일'과 사이드바 배지에 2배 이상 좌석 수가 뜬다. 사용량은 이용권 관리에만 쓰고 인사평가에 쓰지 않는다.

### D-1 — 사용 신청·반납 (F4, v2.1)
1. [직원] Slack에서 "AI-A 쓰고 싶어요", "Claude API 사용해야 해요", "Acrobat 이제 안 써요".
2. [에이전트·의도 분류] 사용 신청 / 반납·중단으로 분류한다. 제품이 분명하지 않으면 승인 제품 이름을 보여 주고 하나만 되묻는다.
3. [에이전트] 좌석형 제품은 `create_action_plan(seat_assign)`, API 제품은 `create_action_plan(api_access)`, 반납은 `create_action_plan(seat_reclaim)`을 만든다.
   - 좌석형이고 **남은 좌석이 있으면** 시스템이 바로 승인·배정한다(`approver_id=sys`). 직원에게 "바로 배정됐어요."
   - **남은 좌석이 없거나** API·반납이면 승인 대기. 좌석이 없는 신청에는 "승인 시 1석 추가 구매(Mock) 후 배정" 근거를 붙인다.
4. [시스템] 승인 대기 건에 `review_seat_request`로 AI 의견을 붙이고, Slack 워커가 관리자에게 DM을 보낸다(요약 + AI 의견 + **[승인]/[반려]**).
5. **[관리자]** Slack 버튼이나 웹 콘솔 승인 대기에서 결정한다. 승인하면 바로 실행한다.
   - 좌석 배정: 모자란 좌석만큼 추가 구매(Mock) 후 배정. **구매 좌석 수를 넘겨 배정하지 않는다** (실행 직전 재검증).
   - API 사용: 요청자 이름의 테스트 프로젝트와 키를 만든다.
6. [Slack → 요청자] 사용 안내. **비밀번호·키 값은 Slack에 보내지 않는다.**
   - 좌석 제품: 접속 주소, 아이디 = 회사 이메일, 비밀번호 없음(회사 SSO), 로그인 방법.
   - API: 키 앞부분 + 본인만 **한 번** 여는 링크(`/key/{id}`, 24시간). 열면 서버에서 키 값을 지운다(`key_handoffs.secret = NULL`).

### D-2 — 미지원 요청 (F5, 축소)
B의 8번으로 쌓인 기록을 관리자가 "미지원 요청" 화면에서 본다. 같은 기능 3건 이상·2개 부서 이상이면 검토 기준 충족으로 표시한다. 후보 제품 비교는 후속.

### E — 비AI 구독 (v2 추가)
Adobe 좌석 60석 계약을 시드에 넣고, D-1과 C를 같은 흐름으로 시연한다. 직원이 "계약서 PDF 편집"을 물으면 에이전트가 AI 대신 Acrobat 이용권을 안내한다.

## 5. 아키텍처

v1과 같다. 바뀐 것은 Slack 경계와 배치 트리거뿐이다.

| 계층 | 하는 일 | AI |
| --- | --- | --- |
| Slack 봇 (Bolt, Socket Mode) | 직원 DM·멘션 수신 → 에이전트 작업 생성, 버튼 응답 → 백엔드 | 없음 |
| 관리 화면 (Vue) | 직원 뷰(시연 대체), 관리자 뷰 | 없음 |
| 에이전트 런타임 (LangGraph) | 의도 분류, 역할 프로필, 도구 호출 루프, 승인 게이트, checkpointer | 있음 |
| 업무 MCP · 문서 검색 MCP (FastMCP) | 역할별 도구 노출, 입력 검증, 백엔드 호출 | 없음 |
| 백엔드 (FastAPI) | 권한, 처리 요청 상태, 알림 정책, **Slack 발송**, 감사 로그, 실행기 | 없음 |
| 배치 (APScheduler) | 사용량 10~30분, 업데이트 주 1회. 조건 충족 시 시스템 계정으로 에이전트 호출 | 없음 |
| Mock 벤더 | OpenAI, Anthropic, xAI, Canva, Adobe(v2) | 없음 |

Slack MCP는 쓰지 않는다. 수신은 봇이, 발송은 백엔드가 한다. 에이전트는 Slack을 직접 만지지 않는다.

## 9. 알림 정책 — 코드 규칙 (v2)

HRD 승인을 대신하는 안전장치다. 백엔드 발송 모듈이 전부 검사하고, 거른 이유를 `review_runs`에 남긴다.

| 규칙 | 값 |
| --- | --- |
| 개인·팀 제안 상한 | 팀당 주 2건 |

| 발송 조건 | 관련성 근거(relevance)가 있는 제안만 |

| 팀별 스위치 | 관리자가 끄면 그 팀에는 보내지 않고 기록만 |
| 사용 의사 확인 기한 | 5영업일. 무응답은 유지, 관리자에게만 알림 |

## 12. 에이전트 그래프 변경 (v2)

현재 구현(`apps/agent_runtime/AGENT_DESIGN.md`)의 루프는 유지하고 앞단에 업무별 분기를 붙인다.

```mermaid
flowchart TD
    START --> prepare --> classify_intent
    classify_intent -->|제품·모델 추천| collect_conditions
    classify_intent -->|이용권·제품 요청| call_model
    classify_intent -->|업데이트 검토 (시스템)| call_model
    classify_intent -->|알림 조사 (시스템·관리자)| call_model
    classify_intent -->|일반 질문·정책| call_model
    collect_conditions -->|조건 부족| ask_user --> END
    collect_conditions -->|충분| call_model
    call_model --> check_limits
    check_limits -->|조회 도구| tools --> call_model
    check_limits -->|변경 도구| approval_gate
    approval_gate -->|승인| tools
    approval_gate -->|거절| call_model
    check_limits -->|답 또는 한도| finalize --> END
```

| 추가 노드 | 하는 일 |
| --- | --- |
| `classify_intent` | 요청을 다섯 의도로 분류하고 프롬프트·도구 부분집합을 고른다. 시스템 계정은 prompt_name으로 바로 정해진다 |
| `collect_conditions` | F2 필수 조건 5개를 확인한다. 부족하면 질문 하나로 묶어 `ask_user`로 보낸다 |
| `ask_user` | 질문을 답으로 돌려주고 종료. 직원이 답하면 같은 thread로 이어진다 |

State에 `intent`, `conditions` 두 필드가 늘어난다. Harness 8요소는 그대로다.
