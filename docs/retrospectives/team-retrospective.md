# NODI 프로젝트 회고

> AI 서비스 개발 Mini-project · 2026.10.26
>
> 팀원들의 회고와 PM의 프로젝트 진행 경험을 공통 주제로 정리한 문서입니다. 아래 개선안은 다음 프로젝트에서 적용할 제안입니다.

## 1. 프로젝트를 돌아보며

NODI는 사내에 도입한 AI와 소프트웨어를 직원이 더 잘 활용하고, 관리자가 사용 현황과 이용권을 관리하도록 돕는 서비스다. 기존 AI Agent Capstone에서 출발한 아이디어와 구현을 바탕으로, 이번 프로젝트에서는 직무별 AI 활용 안내, 이상 사용 안내·분석, 이용권 관리의 사용자 흐름을 구체화했다.

AI 도입과 활용이라는 시의성 있는 문제를 선택하고 기존 서비스와의 차별점을 고민했다는 점이 의미 있었다. 특히 도구를 도입한 이후 실제 업무에서 활용하지 못하는 직원의 어려움과, 도입한 자산을 운영하는 관리자의 어려움을 함께 바라보려고 했다.

## 2. 잘한 점 · Keep

### 실제 업무 상황을 기준으로 기획한 점

사용자의 입장에서 어떤 기능이 필요하고 어떤 순서로 이용해야 편리할지를 고민했다. 같은 정보라도 직원에게는 업무에 바로 적용할 수 있는 안내가 필요했고, 관리자에게는 현재 상태와 판단 근거가 필요했다. 사용자 관점에서 서비스를 구성하는 과정은 즐거우면서도 쉽지 않았지만, 기능의 목적을 구체화하는 데 도움이 되었다.

### 팀원들의 아이디어로 주제를 발전시킨 점

초기 아이디어에서 어려움을 겪더라도 큰 주제 안에서 여러 관점을 제시하며 과제와 사용자 문제에 맞는 방향을 찾았다. 이 과정에서 팀원들의 아이디어와 다른 시각이 기획을 발전시키는 데 기여했다. 초기에 고민한 문제가 이후에도 다시 등장한다는 사실을 경험하면서 문제 정의의 중요성을 확인했다.

### 기획과 코드의 관계를 이해하려고 노력한 점

AI로 작성한 코드도 실제로 어떤 일을 하는지 이해하고 기획한 동작과 맞추려고 노력했다. 기능을 구현하는 과정에서 기획팀과 개발팀이 서로의 의도를 더 잘 이해하려고 했고, 기술 구현뿐 아니라 명확한 요구사항과 소통이 결과에 영향을 준다는 점을 배웠다.

## 3. 어려웠던 점 · Problem

### 초기 합의가 부족하면 다시 처음으로 돌아가게 됨

초기 문제 정의에서 막힌 내용을 충분히 해결하지 않고 진행하면, 기능을 구체화하는 단계에서 같은 질문으로 돌아오게 되었다. 사용자, 기능의 목적, 승인과 반려 같은 정책이 명확하지 않으면 개발과 문서 작업 모두 다시 확인해야 했다. 초기 기획에 쓰는 시간은 후반의 재작업을 줄이기 위한 투자라는 점을 느꼈다.

### 구현에 집중하면서 소통과 검증 시간이 부족해짐

기획팀과 더 잘 소통하려고 노력했지만 기능 구현을 서두르면서 충분한 설명과 확인에 시간을 쓰지 못한 아쉬움이 있었다. 큰 계획에서 벗어나지 않았는데도 검증과 수정에는 예상보다 많은 시간이 들었다. 기능 개발 일정과 별개로 통합 확인, 오류 수정, 제출물 정리 시간을 확보할 필요가 있었다.

### Slack·웹·서버·DB의 연결이 복잡했음

사용자는 Slack과 웹을 오가며 기능을 이용하지만, 내부에서는 서버 처리와 DB 상태까지 일치해야 업무가 완료된다. 한 화면이나 개별 기능이 정상이어도 전달·저장·조회 중 한 단계가 맞지 않으면 사용자 흐름은 끊어질 수 있었다. 따라서 각 기능의 구현 여부와 함께 처음부터 끝까지 이어지는 동작을 확인해야 했다.

### 테스트 데이터의 일관성을 유지하기 어려웠음

Docker를 활용해 실행 환경을 맞추려고 했지만, DB 초기 데이터 수정이 잦아 같은 조건에서 테스트하기 어려웠다. 실행 환경을 통일하는 것과 테스트 데이터를 고정하는 것은 별도의 작업이라는 점을 배웠다. 어떤 코드와 데이터로 확인한 결과인지 함께 남길 필요가 있었다.

### 변경된 정책이 문서에 남는 문제

논의 과정에서 승인·반려·반납 정책과 기능 구성이 바뀌면서 시나리오, 설계서, 발표자료의 설명을 함께 고쳐야 했다. 결정 내용을 한곳에서 관리하고 영향을 받는 문서를 연결하지 않으면 이전 설명이 남을 수 있다는 점을 확인했다.

## 4. 다음 프로젝트의 실행 제안 · Try

| 개선 과제 | 적용 방법 | 완료를 확인하는 기준 |
| --- | --- | --- |
| 초기 문제 정의 | 대표 사용자·문제·사용 이유를 짧은 문서로 합의한다. | 팀원들이 같은 사용자 문제와 핵심 가치를 설명할 수 있다. |
| PRD와 정책 합의 | 정상 흐름과 예외 흐름, 사람의 결정 범위, 완료 조건을 개발 전에 확인한다. | 승인·반려·부족·무응답 등의 분기마다 기대 결과가 있다. |
| 회의 후 실행 관리 | 결정 사항·미결 사항·담당자·확인 시각을 기록한다. | 막힌 작업에 다음 행동과 담당자가 연결되어 있다. |
| 통합 검증 조기 시작 | 대표 시나리오를 Slack에서 시작해 저장·알림까지 실행한다. | 화면·DB·메시지의 결과가 일치한다. |
| 공통 테스트 환경 | 코드 버전, DB 초기 데이터, 계정·권한, 외부 연동 조건을 기록한다. | 다른 팀원이 같은 조건으로 결과를 재현할 수 있다. |
| 변경 이력 관리 | 정책 변경 시 PRD·테스트·화면·발표 문구의 영향을 함께 점검한다. | 최종 구현과 제출 문서의 설명이 일치한다. |
| 일정 배분 | 구현 일정과 별도로 검증·수정·제출물 정리 시간을 확보한다. | 제출 전 대표 흐름과 남은 문제를 확인할 시간이 있다. |
| PR 참여 | 각자 설명할 수 있는 변경 범위를 초기에 정하고 검토를 요청한다. | 본인 PR의 변경 내용과 병합 여부를 확인할 수 있다. |

## 5. 팀이 얻은 배움

AI를 활용하면 초안과 코드를 빠르게 만들 수 있지만, 무엇을 만들고 어떤 결과를 완성으로 인정할지 정하는 책임은 팀에게 남는다. 이번 프로젝트에서는 명확한 문제 정의와 기획, 서로의 의도를 이해하는 소통, 동일한 조건의 검증이 모두 필요하다는 것을 경험했다.

기능을 설명하는 문장과 실제 사용자의 경험 사이에는 여러 처리 단계가 있다. 앞으로는 사용자의 시작 행동부터 결과 확인까지 같은 시나리오로 기획·개발·검증을 연결하고자 한다. 실제 서비스 출시 이후에는 활용 안내의 유용성이나 업무 처리 시간처럼 사용자에게 돌아가는 가치를 확인해야 하며, 현재의 내부 검증을 실제 기업의 비용 절감 성과로 확대해 해석하지 않는다.

**이번 프로젝트의 가장 큰 배움은, AI로 구현 속도가 빨라질수록 팀이 공유하는 문제 정의와 완료 기준을 더 명확하게 만들어야 한다는 점이다.**
